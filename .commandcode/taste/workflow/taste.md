# Workflow

- Prefers phased, strictly-scoped execution plans modeled on the project's `ai-plan-relay-workflow` skill: risk levels, explicit authorized file lists (modify/add-only/forbidden), one phase at a time, and "next phase" prompts handed off between stages. Confidence: 0.9
- Wants independent verification of each stage that does not trust the executing AI's self-assessment: inspect the workspace (git status, diffs), run builds and smoke tests, and produce evidence-based results. Confidence: 0.95
- Wants review findings classified as Blocking / Carry-forward / Closeout-only, with conclusions Pass / Advance with closeout / Fail; only Blocking issues require rework in the current phase, and non-blocking items must be tracked in a complete Closeout Ledger (ID, evidence, impact, exact files, acceptance criteria, owning stage). Confidence: 0.95
- Wants generated next-phase / handoff prompts to be complete and self-contained so the user does not need to supply additional context. Confidence: 0.9
- Requires a baseline verification gate before starting work: independently verify the exact HEAD commit and a clean working tree first (and read the project's AGENTS.md), and stop immediately without touching files if either does not match the authorized baseline. Confidence: 0.9
- Treats user-owned tooling/workflow configuration files (e.g., `.agents/`, `.codex/`, `.cursor/`, `AGENTS.md`) as untouchable: they must be preserved, never modified or deleted, and never staged into stage commits. Confidence: 0.9
- Wants an acceptance matrix with every item explicitly marked Pass / Fail / Unverified plus evidence, and a receipt that never hides failures, skipped items, deviations, blockers, or unverified results — including actual exit codes and raw command output — and expects it delivered as a compact receipt (紧凑回执) plus the review package per the skill's handoff format. Confidence: 0.9
- Wants hard-stop discipline at stage boundaries: never expand the authorized file scope, never touch forbidden projects (WPF/Native/database), and explicitly confirm the stage stopped without entering the next unauthorized stage. Confidence: 0.9
- Wants executors to run a fixed self-review loop (direction / behavior / diff / validation / acceptance) and fix in-scope defects themselves rather than bouncing fixable issues back to the planner. Confidence: 0.9
- Wants commits only when every acceptance criterion passes and there are no blocking findings, with a clean worktree, the exact specified commit message, and no amend. Confidence: 0.9
- Keeps diffs minimal even within an authorized scope: if a scoped file needs no change because its semantics already satisfy the contract (e.g., a retry policy already permanent), leave it untouched and report that explicitly rather than making cosmetic edits. Confidence: 0.9
- Wants out-of-scope defects observed during a phase recorded in the Ledger with a new ID and owning stage (Closeout) instead of being fixed on the spot; in-scope defects are fixed, out-of-scope ones are tracked with evidence for later stages. Confidence: 0.9
- Allows a minimal, unavoidable out-of-scope edit when it is a compile-required ripple of an in-scope rename (e.g., a non-authorized file that references a renamed enum member must be updated or the build breaks): treat it as a pure rename, no behavior change, verify the diff is minimal, and record it in the Ledger as a scope deviation rather than silently expanding scope or stopping. Confidence: 0.85
